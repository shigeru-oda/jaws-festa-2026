# JAWS FESTA 2026 in AKITA トークスクリプト

- **セッション**: CSV置くだけ構成は壊れずに間違う ― 秋田のオープンデータで検証するS3 Tables
- **日時/場所**: 2026-11-07(土) 13:40〜13:55 / あきた芸術劇場ミルハス
- **トラック**: クラウドセントリック
- **尺**: 15分 / **レベル**: Lv300 / **ライブデモなし**(すべてスクリーンショットと数値)
- **登壇者**: 織田繁
- **公開ページ**: https://jawsfesta2026.jaws-ug.jp/timetable/4268f6be-274a-45f1-b5e3-ec5b56c0a0f7

## 構成の考え方

**同じ集計を2回やる。1回目は間違い、2回目は合う。**

冒頭で「今の秋田」を4つの数字で出し、その数字をオープンデータから出すという課題に落とす。
素の S3+Athena で出すと静かに間違い、S3 Tables で出すと合う。秋田の話とIcebergの話が
同じ集計を共有するので、地元の題材が飾りにならない。

| | 何が起きるか | 気づけるか | 題材 |
|---|---|---|---|
| **第1段** | 列名が変わる | **気づけない**(ヘッダは捨てられる) | 月報人口 36列・26列改称 |
| **第2段** | 列が消える | **値がずれる**(検算も通る) | 人口移動理由 19列→16列 |

どちらも**エラーが出ない**。第1段は値が正しく取れて意味だけが間違い、第2段は値そのものがずれる。

## 使い方

- `話す` がそのまま読み上げる原稿。`表示` がスライドに出すもの。
- `【要実測】` は AWS 上で動かしてから埋める箇所。
- 数字の出典は末尾の「数字の裏取り」。すべて `out/*.json` に実測値がある。
- 尺の再生成: `uv run python scripts/retime_talk_script.py`

## S7 — 「県外転入」は県外転入ではなかった (3:53-5:23 / 90秒)

**表示**: `out/rename_overstate.png`。市部計 1,125 vs 639 / 郡部計 104 vs 45。県計では一致する

> **話す**
> 気づいてほしいのは、2020年版には県外を指す列が**2つあった**ことです。
>
> 検算すると、位置20の値は位置23の県内と位置24の県外の**合計**でした。396行すべて一致します。
> つまり「県外転入」という名前の列に県内と県外の合計が入っていた。
> 2024年の「転入・合計」への改称は、**県による名前の訂正**だったわけです。
>
> この列を県外転入だと信じて集計するとどうなるか。
> 市部計で1,125人、実際の県外は639人。**76パーセントの過大**です。
> 郡部計は104人に対して45人で、**131パーセント過大**。
> 母数が小さいほど県内移動の比率が高いので、市町村別に落とすほど誤差が広がります。
>
> ここが意地悪なところで、**県計だけ見ていると一致します。**
> 県全体では県内移動が打ち消し合うので県内転入の欄が空になり、合計と県外が同じ値になる。
> 県の集計を見て検算したつもりになって、市町村別に落とした瞬間に間違い始めます。

## S8 — なぜ気づけないのか (5:23-6:26 / 62秒)

**表示**: `skip.header.line.count=1` でヘッダ行が捨てられる図。「検出可能な変化が存在しない」
**実機 Athena で確認済み**(2026-08-13): 2024年版を同じプレフィックスに置いた後に
`information_schema` を引いても位置20は `kengai_tennyu_danjokei` のまま。`転入・合計` は現れない

> **話す**
> ではAthenaはこの訂正を教えてくれるのか。**教えてくれません。**
> 2020年版の定義で両方のファイルを読んでも、816行、エラーも警告もゼロで通ります。
>
> 理由は2つあります。1つ目、**ヘッダ行はクエリに入っていません。**
> CSVテーブルは skip.header.line.count で1行目を捨てるので、列名は処理系に一度も渡りません。
> 県が訂正を1行目に書いても、その行は捨てられます。
>
> 2つ目、**検出可能な差分が存在しません。** 位置も値の意味も行数も型も同じです。
> Athenaが気づかないのではなく、**気づく材料が届いていない**。構造上そうなります。

## S9 — 列が消えると値がずれる (6:26-7:39 / 73秒)

**表示**: `out/athena_misread.png`。結婚・離婚 = 117（本当は390）。19列→16列、7列が別項目、3列がNULL
**実機 Athena で確認済み**(2026-08-13): 19列定義で16列ファイルを読み、エラーなし・NULL埋めで通った

> **話す**
> 名前が変わるだけなら値は壊れませんでした。**列が消えるとずれます。**
>
> 4つ目の数字、移動の理由を出すために人口移動理由実態調査を使います。
> 2019年に分類が再編されて、19列が16列になりました。統合と分割と削除が同時です。
>
> 旧定義のまま読むと、結婚・離婚が理由の人数は117人と返ります。
> 正しい値は390人で、117は住宅事情の人数です。
> この1行だけで**7項目が別の項目の数字を返し、3項目がNULLになります。**
> 存在しない「家業後継」にも295が入り、中身は学業です。
>
> ここが要点で、このデータには総数の列があるので検算できます。
> **やってみると1,521行すべて一致します。** ラベルだけが入れ替わっているので足せば合う。
> **品質チェックをすり抜けます。**

## S10 — S3 Tables に入れる (7:39-8:44 / 64秒)

**表示**: 汎用バケット → **テーブルバケット**。Athena CTAS で取り込み。19列 → **28列**

> **話す**
> ではS3 Tablesならどうなるか。
>
> S3 Tablesは汎用バケットとは別種のテーブルバケットを作ります。
> CSVをそのまま置くのではなく取り込み直しで、AthenaのCTASで書き出します。
> 元のCSVを残すなら二重保管になります。
>
> 【要実測】CTASのSQLと所要時間、つまずいた権限エラーを1枚
>
> **Icebergは列を位置ではなく field ID で管理します。**
> 名前が変わってもIDは変わらないので、リネームはスキーマ進化として記録される。
> 名前が違う列は別の列として足されるので、値が別の項目に流れ込みません。
>
> 旧版のテーブルに新版を足すと、列は19から28に増えます。
> 新しい版にしかない9項目が追加され、旧版の行はそこがNULLになります。

## S11 — 同じ集計をもう一度 (8:44-9:50 / 66秒)

**表示**: 冒頭の4つの数字を再掲。素の構成の値とS3 Tablesの値を並べる + snapshot 一覧

> **話す**
> 冒頭の4つの数字に戻ります。S3 Tablesの上で同じ集計をすると、**数字が合います。**
> 列名が変わった年も、分類が変わった年も、同じ1本のSQLで取れます。
>
> 追記のたびにスナップショットが記録されるので、再編前の状態にも戻れます。
> 置くだけ構成なら年度ごとのフォルダを自分で切ることになります。
>
> ただ、正直に言うと**2019年に段差が出ます。** 回答総数そのものが4,481人から6,413人へ、
> 43.1パーセント増えていました。調査の規模か方法も変わったわけです。
>
> **Icebergが保証するのは壊れずに1つのテーブルで読めるところまで。**
> 比較していいかどうかは統計側の判断で、自動化できません。

## S13 — パフォーマンス実測 (10:38-11:55 / 77秒)

**表示**: ローカル実測（CSV 143.5 KB / 0.9 ms 対 Iceberg 39.0 KB / 3.5 ms）
**実機 Athena**(2026-08-13): 1クエリのスキャン量は月報人口 **129,354 bytes** /
人口移動理由 **146,928 bytes**(どちらも2ファイル全体。プルーニングなし)
+ 【要実測】S3 Tables 上の値

> **話す**
> 速さも測りました。
>
> S3 Tablesは汎用バケット上のIcebergよりクエリ最大3倍と謳われますが、
> それはコンパクションで小さいファイルがまとまり、メタデータで読む範囲を絞れる規模の話です。
>
> 手元で測ると、この規模では**CSVを直接読むほうが速い。**
> 143.5キロバイトのCSVが0.9ミリ秒、39.0キロバイトのIcebergが3.5ミリ秒です。
> ミリ秒の桁なので実行ごとにぶれますが、4倍前後の差は毎回同じ向きに出ます。
> Icebergはメタデータを経由するぶん、数十キロバイトではオーバーヘッドになります。
>
> 【要実測】実機 Athena での素の構成 vs S3 Tables の実行時間とスキャン量
>
> しかもAthenaの課金は1クエリ最小10メガバイトなので、この規模では
> スキャン量ではなく最小課金が支配します。
> **速さのためにS3 Tablesを選ぶ理由は、この規模にはありません。**

## S14 — 判断軸 (11:55-12:51 / 55秒)

**表示**: 判断表

| 自分のデータが… | 素の S3+Athena (CSV) | S3 に Parquet | S3 Tables |
|---|---|---|---|
| 列の構成が変わらない | ◎ 十分 | ◎ | 過剰 |
| **列名が変わる** | **気づけない** | ○ 名前で読む | ◎ 進化として記録 |
| **列が増減する** | **値がずれる** | ○ | ◎ |
| 過去の版を遡りたい | 自分で運用 | 自分で運用 | ◎ snapshot |
| 書き込みが同時に走る | 中途半端な状態が見える | 同じ | ◎ アトミック |
| 数MB程度 | ◎ 安くて速い | ◎ | 監視・圧縮の費用が乗る |
| 数百GB以上・小ファイル多数 | 遅くなる | ○ | ◎ 自動コンパクション |

> **話す**
> まとめます。判断の軸はデータ量ではなく、**スキーマが動くかどうか**でした。
>
> 列の構成が安定していてサイズも小さいなら、素のS3とAthenaで十分です。安くて速い。
> 私のデータも、速度だけ見ればそちらが有利でした。
>
> 逆に、**年に一度スキーマが動くデータなら置くだけ構成は危険です。**
> 名前が変わっても気づけず、列が増減すれば値がずれ、検算はすり抜けます。
>
> Parquetでもリネームには強くなりますが、過去の版に戻る仕組みと
> 同時書き込みのアトミック性は付いてきません。そこが要るならS3 Tablesです。

## Q&A 用の手持ち材料

| 想定質問 | 答えの材料 |
|---|---|
| Parquetにすれば済むのでは? | ドキュメントの対応表どおりParquetは名前で読むので、リネームも列の増減も可。**ただし過去の版に戻る仕組みと同時書き込みのアトミック性は付いてこない**。スキーマ進化だけならParquet化で足りる、が正しい |
| Athenaの仕様上の裏付けは? | 公式の「Handle schema updates」に形式別の対応表がある。CSVは途中への列追加も並べ替えも不可、**列の削除は非推奨**と明記。一方で**列名の変更は「可」**。可とは壊れないという意味で、気づけるという意味ではない |
| Glue Crawlerを再実行すれば? | 列名は更新されるので**リネームには気づける**。ただしデータ側からの通知はなく人間が能動的にやる操作。さらに**位置がずれる変更のときは再クロールが逆に壊す**(新しい名前を旧ファイルの位置に割り当てる) |
| 列名を信じるのが悪いのでは? | そのとおり。ただし2020年版には「県外転入」と「転入・県外計」が並存していて、どちらが県外だけかは**データを検算しないと分からない**。名前を疑うコストを毎回払えるか、という話になる |
| 県計では一致するのでは? | 一致する。県全体では県内移動が打ち消し合うので県内転入の欄が空になる。**だから県計で検算すると通ってしまう**。市町村別に落とした瞬間に76〜131パーセントずれる |
| DuckDBで代替できるのでは? | ローカル検証はDuckDBでやった。**DuckDBは列数不一致をエラーにする**(`auto_detect=false`を付けないとHiveの振る舞いにならない)。共有・権限・同時書き込みが要るならS3側に置く判断になる |
| コストは? | 【要実測】S3 Tablesはストレージ + オブジェクト監視 + コンパクションのリクエスト課金。数MBだと監視系の費目が支配的になる見込み |
| コンパクションでどれくらい速くなる? | 私のデータでは**出番がなかった**(ファイル2個)。GB級で試すべき。第三者検証ではコンパクション遅延やコスト増の指摘もある |
| 他県のデータも試したか? | 39都道府県を調べた。19ファイル中11がShift_JIS、ヘッダが1行目にない県が4件(長崎8行目・徳島5行目・佐賀3行目・北海道2行目)、香川は負数を`△`で表記。4県を74列1テーブルに統合して111行を同じ形で取得済み |
| 秋田のカタログ全体の話をもっと | 264データセット・2,261リソース・11形式。分野は17種で行財政53件が最多。ライセンスは262件がCC BY 4.0。全データセットの分野別一覧は`docs/akita-catalog-list.md`、同梱データの台帳は`docs/akita-opendata.md` |

### 4. 事実関係で危ないところ

- **「県外転入」の壊れ方は行の種類で違う**。市町村行では県内+県外の合計だが、
  県計行は県内転入が空なので一致する。スライドに県計の数字を出すと主張と矛盾するので、
  **必ず市部計・郡部計・市町村の数字で見せる**
- **「列名の変更は可」はCSVの話**。Parquetは名前読みが既定なので逆に不可。口頭でも形式を必ず添える
- **速度比較はローカル(DuckDB vs pyiceberg)**。実機の値が入るまでは「手元で測ると」を外さない
- **リネームは「壊れない」**。S7-S8で「値は正しく取れる、意味が間違う」を混同しないよう話す
- **カタログ全体の数字はCKAN APIの実取得**で、`make check` の対象外。
  本番前に取り直すと件数が動く可能性がある
