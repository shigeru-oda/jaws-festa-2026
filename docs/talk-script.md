| **先頭や途中への列追加** | **×** | ○ |

## S9 — S3 Tables に入れるとどうなるか (6:52-8:17 / 84秒)

**表示**: 同じ2ファイルをS3 Tablesへ。19列 → **28列**。同じ行を読むと結婚・離婚 = 390

> **話す**
> では同じ2つのファイルを、S3 Tables に入れます。
> S3 Tables はマネージドなApache Icebergで、専用の「テーブルバケット」を作って、
> そこにテーブルとして取り込みます。CSVをそのまま置くのではなく、
> **取り込み直し**になります。ここは後で費用の話に関わります。
>
> 2013年版で作ったテーブルに2019年版を足すと、列は**19から28に増えます**。
> 新しい版にしかない9つの項目が、列として追加されました。
>
> Icebergは列を位置ではなく **field ID、つまり列ごとのID**で管理します。
> だから名前が違う列は別の列として足される。
> 2013年版の行では新しい項目がNULL、2019年版の行では古い項目がNULL。
> **値が別の項目に流れ込むことがありません。**
>
> 同じ行をもう一度引くと、結婚・離婚は **390**。正しい値が返ります。
>
> 【要実測】S3 Tables 上での取り込みコマンド・所要時間・つまずいた権限エラーを1枚入れる

## Q&A 用の手持ち材料

| 想定質問 | 答えの材料 |
|---|---|
| Parquetにすれば素の構成でもいいのでは? | ドキュメントの対応表どおり、Parquetは名前で読むので途中への列追加も削除も可。**ただし過去の版に戻る仕組みと、複数書き込みのアトミック性は付いてこない**。スキーマ進化だけならParquet化で足りる、が正しい |
| Glue Crawlerに再クロールさせれば? | テーブル定義は更新されるが、**古いファイルは新定義で読まれる**ので位置ずれは残る。Hiveはパーティション単位のスキーマを持てるが運用が複雑になる |
| DuckDBで代替できるのでは? | ローカル検証はまさにDuckDBでやった。共有・権限・同時書き込みが要るならS3側に置く判断になる |
| S3 Tablesのコストは? | 【要実測】ストレージ + オブジェクト監視 + コンパクションのリクエスト課金。数MBだと監視系の固定的な費目が支配的になる見込み |
| 自動コンパクションはどれくらい効く? | 私のデータでは**出番がなかった**(ファイル2個)。第三者検証ではコンパクション遅延や条件次第のコスト増の指摘もある。GB級で試すべき |
| Lake Formationの権限設計は? | 【要実測】2026-03にGlue Data CatalogがIAMベース認可に対応し、単一ポリシーに寄せやすくなった |
| 他県のデータも統合したのか? | 4県(大分6列/神奈川10列/栃木13列/沖縄45列)を`union_by_name`で74列1テーブルにして111行を同じ形で取得済み。栃木は総数列がないので男+女を自分で足した |

### 5. 事実関係で危ないところ

- **「Athenaは列の位置で読む」はCSV限定**。Parquetは名前読みが既定。S7の表で明示しているが、

- **速度比較はローカル(DuckDB vs pyiceberg)**。AthenaとS3 Tablesの比較ではない。
  S12で「手元で測ると」と限定している。**この限定を外さないこと**
- **「他県で質的データを公開している県は見つからなかった」は36県調査の結果**。
  3県(島根・岡山・広島)は未確認なので「見つかりませんでした」までにとどめ、
  「存在しない」とは言わない(現状の原稿はその表現になっている)
